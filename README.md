## 一、为啥会有这事

2026 年 11 月 10 日，随着南山必胜客的两纸律师函，NapCat 项目发布最后一次提交，标题为ending，正式跑路了，同日SnowLuma 仓库也从 GitHub 消失，返回 404，空悲切。24 小时后，一个名为 SnowCatQQ （下简称雪猫，https://github.com/DandanLLab/SnowCatQQ）的仓库出现在 GitHub 上。其对外宣称把 NapCat 与 SnowLuma 两套代码融合且全功能适配 QQ 9.9.37，拥有所谓的56 项独门动作，MCP 接入，全线开源，持续维护

光看名字就知道是要吃nc和sl人血馒头的，打算趁着两个协议端跑路包圆这一块的热度，事实上其开发者称自己的行为为“接续先行者铺下的路”；那么这个仓库在开源社区里究竟是一个什么东西呢？

史家据史直书，一字不改！😡 且不说现在还活着的诸如拉格兰等等或许还更加强大只是社区小而不被发现的实际上相当成熟的小众协议端；事实上倘若雪猫是个好协议端，在开源社区继续维护已经归档的仓库此类行为本身也是个好事——但是这个仓库实在是极为抽象以至于我在多个技术交流为主的QQ群都看到有群u对此事件发表锐评了，本着实事求是的想法，我想我也必须得对此仓库进行轰轰烈烈的真理大讨论了

全文除了玩梗不掺杂纯粹人身攻击，要说不带感情来评价这坨矿石巨奋是不可能的了，我不相信有人看完这个仓库底下的一些issue能忍住不笑出来以至于不产生“这波贪了应该再等几个月留着春晚看的”的想法——故请读者读完自行得出自己的结论，不要跟着我起哄，一人做事一人担😡

## 二、背景：上游熄灯

理解这件事，需要先理解它落脚的那块地。

NapCat 是社区里维护时间最长、用户量最大的 QQ 协议端之一。2026 年 11 月 10 日，它的作者在仓库里留下最后一次提交，README 改成了：

> 到这里告一段落。

同年 11 月，SnowLuma 仓库从网络消失。项目自己的公告里记录了这件事：

> 同一日，SnowLuma 原仓库自网络消失，返回 404，未留片语。一个宣布倒计时，一个直接退场。

笔者核查了当前状态：NapCat 仓库已经被清空，只剩两个提交，内容分别是“Keep README only”和“docs: ending”。SnowLuma 原地址仍返回 404。

这就是 SnowCat 出场的背景。一个空出来的生态位，一个真实存在的需求。

## 五、授权：三份文件，三个说法

仓库根目录的 LICENSE，原文如下：

> 1. Usage and Reproduction:   Unauthorized use, reproduction, modification, or distribution of this code is prohibited without explicit permission from the main author of the NapCat repository.2. Redistribution:   Minor modifications and extensions are allowed for redistribution purposes, but the modified code must not be publicly released.3. Non-Commercial Use:   This code is not to be used for any commercial purposes.

版权行写作：Copyright © 2024 Mlikiowa。

这三段的含义是：修改后的代码不得公开分发。而这个仓库做的全部事情，就是修改这份代码并公开发布。

第二份文件，在 packages/snowcat-webui-frontend/LICENSE：

> MIT LicenseCopyright (c) 2024 bietiaop

而这个目录，README 把它列在自研部分：

> 雪猫控制台（React + Tailwind + HeroUI 全面重制）

第三份说法，在 README 顶部的徽章上。它最初写的是 License: MIT。

2026 年 11 月 14 日 09:52，提交 4b647c8 才把它改为 License-NapCat_Limited_Redistribution。

作者在 issue #45 里的解释原文：

> 徽章是错的，LICENSE 是真的。badge 沿用模板时没核对实际授权文本，这是终审失误。

*这不是法律判断。这是一个打开 LICENSE 读三行就会发现的问题。它连续四天没有被发现，直到有人在 issue 里贴出原文。*

## 八、声明与事实：四组对撞

### 8.1 一字节未动，与系统级硬改

README 写：

> 全功能运行于 QQ 9.9.37-54395（官方最新版）主进程内，QQ 本体一字节未动。V8 编译器通道注入，官方最新版原生运行，QQ 本体零改动。

同仓库 ARCHITECTURE-AUDIT.md 标题：

> SnowCat 雪猫：融合魔改 QQ 客户端（NapCat + SnowLuma 合体）

同文档“硬改点清单”第五条：

> 注册表劫持——QQ 卸载项 UninstallString 指到 D:\...\OneKey\...\Uninstall.exe状态：✅ 实锤，系统级硬改

而 release-tools/build/snowcat-run.ps1 第 85 至 92 行，实际做的事情是：

> foreach ($bad in 'dbghelp.dll', 'dbgeng.dll') {    $p = Join-Path $app $bad    if (Test-Path $p) {        Move-Item $p "$p.disabled" -Force    }}Copy-Item $srcDll (Join-Path $Shell 'winmm.dll') -Force

把 QQ 目录下的两个系统 DLL 改名，然后把一个名为 winmm.dll 的文件复制进去。

### 8.2 无任何外发

前端 pages/dashboard/about.tsx 第 81 行：

> 一切动作都在本地执行，代码全开源白盒可查，无任何外发。

pages/dashboard/index.tsx 第 166 行，渲染了 Hitokoto 组件。

components/hitokoto.tsx 第 23 行：

> request.get<IHitokoto>('https://hi.logacg.com/')

每次打开控制台首页，都会向这个第三方地址发一次请求。

关于 rkey，需要单独说清楚：packages/snowcat-core/apis/file.ts 定义了两个服务地址，第一个是明文 HTTP。笔者读完了 helper/rkey.ts 的 refreshRkey 实现，确认它是 GET 拉取，不是外发本机凭据。准确的表述是：它把图片解密所依赖的 rkey 外包给了两个第三方服务，其中一个是明文 HTTP。这一点不能写成“泄露凭据”。

### 8.3 159 条记录里没有 37

packages/snowcat-core/external/appid.json 共 159 条版本记录。Windows 平台最新的五条是：

> 9.9.31-49738、9.9.32-50828、9.9.32-50969、9.9.33-52230、9.9.35-52892

没有 9.9.37。

查不到时的回落顺序是：按完整版本号查表，查不到按大版本扫 QQ 安装目录，再查不到就用硬编码的 537246092。这个号在表里属于 9.9.15-28060。

issue #73 里三位用户报告的现象与此同族：注入器日志有 READY hooks=4，PATCHED 那一行始终不出现。其中一位补了对照实验——把同一个 DLL 放进带 Low 完整性标签的目录，PATCHED hit=internal_index origLen=59 就出现了。

### 8.4 版本号

构建流程里有一句：从 NapNeko/NapCatQQ 拉最新 tag 注入版本号。

那个仓库的 tags 现在是空数组。

所以每次构建拿到的都是兜底值 1.0.0-dev。而 README 上挂的徽章是 v6.0.0。

## 十五、社区坐标：这不是第一次

要理解这件事在开源社区里的位置，需要提到一个先例。

2026 年 10 月 4 日，社区用户 cubk1 在该仓库提交了 issue #59“测评和反馈”，获得 373 条评论。11 月 16 日实测，该仓库 263 星。

> 本Issue生成格式取自cubk1的issue数据集蒸馏skill，经过能工智人显著修改改进。

也就是说，这套批评方法不是即兴的，它有明确的来源和前例。

两个项目的结构对照：

|  | Forbric（2026-09-10） | SnowCat（2026-11-11） |
|---|---|---|
| 声称 | 一个实例加载三种模组生态 | 两个 QQ 协议端融合，全功能适配最新版 |
| 实质 | 两套不兼容的模组体系硬合并 | 两套协议端代码硬合并 |
